## 01. 從老闆到流程設計師

### 1.1 上次我們學會當老闆（P3）

| 要說清楚的事 | 問自己 |
|---|---|
| 要什麼成品 | 做完我會拿到什麼？放在哪？什麼格式？ |
| 有什麼限制 | 哪些可以動、哪些不能動？ |
| 怎麼算做完 | 我要怎麼驗收？ |

> 上次的重點是：**不要讓 AI 猜。**

💬 老師補充：
- 要告訴它哪些可以動、哪些不能動，不然它有時會把你覺得不應該動的東西「幫你動掉」。
- 從 Prompt 開始一路以來的原則：提供**足夠充分、正確的資訊**，以及**不要讓 AI 猜**，把需求、指引講清楚。

### 1.2 最後我們要出去吹牛的那張圖（P4）

| 範圍 | 名詞 |
|---|---|
| Chat Bot | Prompt Engineering、Context Engineering |
| AI Agent | Harness Engineering、**Loop Engineering**、**Graph Engineering** |

- 今天要補完最後兩格！

💬 老師補充：
- **Prompt Engineering**：怎麼下好 prompt——最後學到最厲害的技巧就是**跟 AI 討論**。
- **Context Engineering**：怎麼把正確的資訊交給它——RAG 是一種方法，今天再做一次的 LLM Wiki 是另一種方法。
- **Harness**：告訴 AI 怎麼做事，是我們要設計的（AI Agent = AI Model + Harness）。今天的 Loop、Graph 都算是 **Harness 設計中的兩個技巧**，沒有新的東西。
- 不學的危險：出去聽人家說「我們現在都在寫 loop」，聽起來好像懂，但不知道它在幹嘛。今天之後吹牛圖完全齊備，「人家再也考不倒我們」。

### 1.3 但我們老闆還是一直盯（P5）

> 你：交辦工作！ → AI：做出一版。 → 你：發現第 5 頁字太多（檢查） → 再一次……
> **這就是 loop！**

💬 老師補充：
- loop（迴圈）其實很簡單，之前就做過：上上週 Reflection 的例子——作者 AI 寫文章 → 審查員 AI 指出哪裡不好 → 回到作者照意見修改 → 新版本再給審查員看……來來回回繞圈圈，就是 loop。
- loop 變重要的關鍵是需要一個**判斷**：通常不會設「做三次就結束」，而是希望**做到好**——要有一個評判的機器人說「這篇夠好了，放行」；不夠好就一直進入迴圈修改。
- 也可能**永遠達不到標準**，所以要設停損點：例如已經改了五次、可能沒希望了，就先停下來檢查發生什麼事；或寫的過程發現資訊不夠，先停下去收集更多資料。

### 1.4 今天的路線圖（P6）

1. 換工具：Code Agent
2. 觀念：Prompt → Loop → Graph
3. 實作一：先討論，再建 LLM Wiki
4. 實作二：主題 → HTML 簡報
5. 拆解你自己的工作

💬 老師補充：
- 用 LLM Wiki 建立知識庫，作用跟 RAG 一樣——那個 wiki **大部分時間不是給我們看的，是給 AI 看的**。
- 上週違反了課程原則：因為時間關係**沒有先跟 AI 討論**就請它把 LLM Wiki 建起來；這週先討論，看會不會做得比較好。
- RAG 只做出系統、從來沒去查資料，就等於沒有應用；LLM Wiki 也一樣，所以今天要從 wiki 做出 **HTML 簡報**（教學簡報或任何主題都可以），並示範導入 loop、graph 之後有什麼差別。
- 重點是**把你自己的工作流程想清楚**，每個人不一樣：老師示範時假設有五個節點（node），**不要背、不用一定做出這五個節點**，老師會這樣想，你不一定會。每個人用同樣的 AI 做 AI agent，也會長得不一樣。

## 02. 這次換用 Coding Agent

### 2.1 上週有同學發現（P8）

> 「Gemini 的對話介面讀不到我電腦裡的資料耶……」「Antigravity 可以！」

💬 老師補充：
- 上週很多同學還沒下課就發現：Gemini 的 **Windows 版**沒辦法讀到自己電腦的資料夾。
- 再強調一次：**AI 可以管理你電腦的資料夾是非常重大的事**——它要模仿你做事，而你平常就是在電腦裡寫報告、整理資料。做不到的話「最大的特點就沒了」，雖然有別的方式，但會跟平常的工作習慣很不一樣。AI agent 不一定要在你的電腦裡做，但本學期特別推薦，因為比較像我們平常做事的樣子。
- Antigravity 也是 Google 的；選 Google **唯一的理由是有學生方案**。作業要用 Claude、ChatGPT 當然可以，你信任哪個就用哪個——只是要做到這些事都需要付費。

### 2.2 Work Agent（P9）

| 工具 | 模式／特色 |
|---|---|
| ChatGPT | Work（／Codex） |
| Claude | Chat 整合（／Code） |
| Gemini | — |
| OpenWorker | 開源並且可用開源模型 |
| GrokBot | 純雲端 |
| Muse | — |

💬 老師補充：
- 「Work Agent」（工作的代理人）是老師自己取的名字：比較接近我們習慣的對話機器人樣子。Claude 已經把原本叫 Cowork 的功能整合進 Chat。
- 老師更正投影片：這一頁 ChatGPT 應該只有 Work、Claude 也不該有 Code——Codex、Claude Code 是下一頁的東西。
- **OpenWorker**：未來在企業裡想用**開源模型**時的選擇。學期初本來計畫教，但開源模型要夠厲害才能做好 agent，有點辛苦，自己的電腦甚至跑不動；要用比較大的模型，還是得付費（在別人的電腦上跑大型開源模型的付費服務）。所以放棄了，但想試試看也可以。

### 2.3 Coding Agent（P10、P12）

| 工具 | 公司 | 說明 |
|---|---|---|
| **Antigravity** | Google | 今天主示範 |
| Claude Code | Anthropic | 有訂閱歡迎使用 |
| Codex | OpenAI | 有訂閱歡迎使用 |
| OpenCode | 開源 | 可以接任何模型 |

- **今天的做法，四套工具都通用。**

💬 老師補充：
- 在 Google 體系下（學生升級成 Plus），能做這件事的就是 Antigravity——Google 的 Coding Agent。
- Coding Agent 開始**深受重視**應該是從 **Claude Code** 開始（不是說它第一個）：打法很正確，讓大家知道這東西能做什麼。不然用 n8n 這類工具設計，要自己處理、自己寫程式的東西太多。
- 大家後來發現 Claude Code **不一定是寫程式才需要**（「名字取錯了」）——更正確地說，它會**用你本來用電腦的方式**去做你想做的事，因為它能碰觸你的檔案。後來出了 Cowork、又分野，現在兩個陣營越來越接近。今天也不是要寫程式，是要做 LLM Wiki。
- 以前 coding agent 都在**終端機**下打字，現在也有介面。用法**一模一樣**；學會後推薦在終端機執行——給老闆看時「老闆一定會更加感動，覺得這個看起來真的是內行的」，做的事其實一樣。今天示範的是看起來像網頁、其實是 App 的版本。
- 老師的「派別」**比較不記指令**：指令就是某種快捷鍵，用久了為了方便自然會記；不記指令，功能也一樣。

### 2.4 一樣一個專案資料夾開始（P11）

- 在自己電腦上開一個**專案資料夾**，讓你的 AI 有**存取權限**。

💬 老師補充：大部分時候為了比較像我們在電腦上自己做事的樣子，會打開一個專案資料夾（跟上次一樣）；但再強調，這些基本上都可以，你連要不要用 Coding Agent 都不一定。

### 2.5 Work Agent 和 Code Agent 其實很像（P13）

| | Work Agent | Code Agent |
|---|---|---|
| 代表 | ChatGPT Work、Claude、OpenWorker | Antigravity、Claude Code、Codex |
| 預設看到 | 成品和摘要 | 每一行修改（diff） |
| 版本控制 | 要自己記得 | **git 是基本盤** |
| 驗證 | 多半靠人讀 | 跑測試、跑腳本 |
| 資料夾・手冊・Skills | ✓ | ✓ |

💬 老師補充：
- 兩者已經非常非常接近，「其實我等一下說的也基本上不是真的是這個樣子」。
- Coding Agent 的「靈魂」在終端機裡。寫程式的人很喜歡做**版本控制**，用一個叫 **Git** 的東西（我們用過的 GitHub 就是 Git 的網頁版）：做一做發現某個地方爛掉了，可以回到原來的地方。
- Work Agent 也可以碰到終端機、也能做這件事，但要特別告訴它「幫我去做」，比較卡、不那麼順暢，「不是內建的樣子」。

### 2.6 今天多學兩個工程習慣（P14）

| 習慣 | 意義 |
|---|---|
| **git** | 每一步都能回去，看得出 AI 改了什麼 |
| **可以執行的檢查** | 「做完了」不是 AI 說了算，是**腳本**說了算 |

> 說「檢查一下」，**不算驗證**。

💬 老師補充：
- 今天會加入 Git，但不會教太複雜，**沒成功也沒關係**——像之前直接把整個專案拖到 GitHub 上，也接受。
- 順便理解外面工程師怎麼做：在人家面前示範 AI agent 時，在終端機打一打、上 GitHub，「特別是沒有真的很懂的老闆，一定覺得厲害」——事實上跟旁邊用 ChatGPT Work 做出來的是一模一樣的東西。

### 2.7 員工手冊各家都看得懂（P15）

| 檔名 | 適用 |
|---|---|
| `AGENTS.md` | 通用 |
| `CLAUDE.md` | Claude Code |
| `GEMINI.md` | Gemini |

- 用 Claude Code 的同學，`CLAUDE.md` 裡寫一行 `@AGENTS.md` 就好。
- Antigravity 也會讀 `AGENTS.md`，換工具不用重寫。

💬 老師補充：
- `.md` 就是 **Markdown** 檔案——「非常奉勸大家一定要去學」：很簡單、很標準（做 Colab 時也用過），世界上很多人用它表示、修飾一篇文章，標示超連結、圖片等。
- 開始時會**跟 AI 一起討論出** AGENTS.md。Gemini 其實比較喜歡 GEMINI.md，今天試試 AGENTS.md。
- 如果中途好奇「Claude 真的比較厲害嗎？」換給 Claude 做（預設讀 CLAUDE.md）也沒什麼大事：跟它說「先讀一下 AGENTS.md」，它讀完就能繼續做這個專案。

## 03. 從 Prompt 到 Loop 和 Graph

### 3.1 有人說：不要寫 prompt，寫 loop（P17）

| 人物 | 身分 | 說法 |
|---|---|---|
| Boris Cherny | Claude Code 負責人 | 「我的工作是寫 loop。」 |
| Peter Steinberger | OpenClaw 作者 | 「別再對 coding agent 下 prompt，去設計替你下 prompt 的 loop。」 |
| Addy Osmani | 2026 年 6 月命名 loop engineering | 「把你自己從下 prompt 的人換掉。」 |

💬 老師補充：
- 這裡很多東西是讓大家「以後出去外面可以去嚇一下人家」的。寫 loop 變成很紅的事，大概是從 Claude 這邊來的。
- 「我現在基本上都不寫 prompt，都只寫 loop」——這句話真的令人聽不懂，因為**我們唯一可以控制 AI 的方法就是寫 prompt**，loop 也是 prompt，只是 prompt 裡面包含了 loop 的概念。

### 3.2 咦？loop 不也是 prompt 嗎？（P18）

> 「Loop 不是也在寫 prompt 嗎？」「對！差別在你寫的是什麼。」

| 寫 prompt | 寫 loop |
|---|---|
| 這一輪要做什麼 | 一份**會自己執行的規格** |

💬 老師補充：寫 loop 比較是把 prompt **寫得很清楚，而且有檢查**——有一個迴圈去檢查一個東西。

### 3.3 最早的 loop 只有一行（P19）

```bash
while :; do cat PROMPT.md | claude ; done
```

- Geoffrey Huntley 的 **Ralph loop**（2025 年 7 月）：同一份 `PROMPT.md`，每一輪都重餵一次。
- 讓它運作的是 prompt 以外的東西：**重複、檢查、用檔案記進度**。
- 看起來很笨，但它真的會動。

💬 老師補充：
- 有興趣可以查查這個源起，滿有趣的：作者名字明明是 Huntley，為什麼叫 Ralph loop？它非常單純，就是寫一個 PROMPT.md，讓它重複執行很多次。
- 概念就是**重複地做，直到做到好**——所以要告訴它什麼叫做到好，也要有辦法檢驗。
- 這些大部分「老實說是要給我們出去外面跟人家介紹的時候要去騙人家的東西」，所以很快放進投影片。老話一句：AI Agent 就是**用我們的方法去教它做事情**。
- **什麼時候該寫成 loop？** 你在跟 AI 聊天中發現來來回回的重複動作：它寫一版、你批評（「不是上次才跟你講不能這樣子」）、它回去改一版……仔細看這幾次其實是**一樣的動作**——**重複的動作就很適合寫成 loop**。需要的是看得出夠不夠好，不夠好就給修改意見再重來。

### 3.4 寫 prompt vs 寫 loop（P20）

| | 寫 prompt | 寫 loop |
|---|---|---|
| 寫的內容 | 這一輪要做什麼 | 目標、完成標準、驗證、停止規則 |
| 下一步誰決定 | 你讀完再寫下一句 | 系統依檢查結果決定 |
| 寫幾次 | 每一輪都寫 | 寫一次，跑很多輪 |
| 你的角色 | 黏著劑 | 設計者、審查者 |

### 3.5 一個 loop 要寫清楚五件事（P21–P22）

| | 項目 | 問題 |
|---|---|---|
| 🎯 | 目標 | 要什麼成品 |
| 🚧 | 限制 | 哪些不能動 |
| ✅ | 完成標準 | 怎麼算做完 |
| 🛑 | 停止條件 | 做不到時，何時停手 |
| ⏰ | 觸發 | 什麼時候開始跑 |

- 前三件，上次當老闆就學過了！
- 完成標準的兩種檢查（P22）：

| 檢查 | 檢查什麼 |
|---|---|
| 🧮 程式檢查 | 測試有沒有過？連結斷了沒？每頁有沒有出處？ |
| 🧑‍⚖️ AI 審查 | 內容有沒有忠於來源？說法有沒有講反？ |

> **不要叫它審自己的作品！** AI 審查要**開新的對話**，只給成品和來源。

💬 老師補充：前三個基本上之前就做過，這裡要增加的是**什麼時候可以停**，以及**什麼時候應該跑這個 loop**（繼續進入 loop 的狀態）。loop 一定要寫清楚的一個重點，就是要去審查。

### 3.6 loop 也要剎車（P23）

| 剎車 | 說明 |
|---|---|
| 硬上限 | 最多改 3 輪 |
| 資料不足就停 | 不要用自己的知識硬湊 |
| 會花錢 | 一個 loop 的 token 遠多於聊天 |

> **沒人看管的 loop，就是在沒人看管下犯錯的 loop。**

💬 老師補充：
- 做到好的時候當然要停；但很多時候也不希望它一直做下去：強硬上限（三次做不好就停）、發現嚴重問題（例如資料不足）就停、花太多錢也可以叫它停——以後做真的偉大、很燒 token 的事時要注意。
- 目標是做出能**完全自動化**跑 loop、不斷修改越來越好的東西；要考量的事「其實我覺得都是常識」，等一下跟 AI 討論時就知道要考慮什麼。

### 3.7 Graph：改變的是「誰在控制」（P24）

| | 例子 |
|---|---|
| 🔁 Loop | 自己反覆改作業，改到檢查表全過 |
| 🕸️ Graph | 學校的申請流程：系辦 → 院 → 教務處，不能跳關，卡住會退回特定一關 |

> 在 loop 裡，**AI 決定下一步**；在 graph 裡，**流程是你事先畫好的**。

💬 老師補充：做事不一定都是一個漂亮的 loop 在轉。例如第一關做完進第二關、第二關做完進第三關，第三關發現不對跳回第二關……到第五關發現某個地方資料不足，甚至可能回到第一關。**由你決定在什麼情境下該跳回哪裡**——它不一定是完美的 loop 形式，是更一般的長相。

### 3.8 其實三個都是圖（P25）

| 做法 | 圖的長相 |
|---|---|
| Prompt | 一個節點，跑一次 |
| Loop | 加一條「回到自己」的邊 |
| Graph | A → B → C，退回的邊可以接到任何一個節點 |

> 順利跑完的 graph，其實就是一條**流水線**。

💬 老師補充：就是離散數學或組合學裡的 graph（圖），沒什麼特別了不起。每個節點就是做一件事：例如 A 節點真的寫出一篇文章、B 節點檢查文章有什麼缺點、C 節點吐出一份評論報告。

### 3.9 好的 graph：大圈很少轉，小圈轉得很快（P26）

```text
檢索 → 大綱 → 逐頁稿 → 渲染 → 交件
  ↺      ↺       ↺        ↺        （小圈：錯了就在附近修，很快）
  ↑──────────────────────────────┘  （大圈：從最後一關退回起點，應該很少發生）
```

> 錯誤要在**離源頭最近的地方**被抓到；常常轉大圈，代表**檢查該往前移**。

### 3.10 讓問題告訴你需要多少結構（P27）

1. **先用 Prompt**：一次性、自己會看。
2. **升級成 Loop**：一直重複說同樣的修正。
3. **拆成 Graph**：loop 每次都整份重來、各階段標準不同。

> 不一定要堅持用 graph。

💬 老師補充：
- 其實**全部都是在寫 prompt**，只是把 loop 的概念（驗證、重複做到可以才放行）加進去；比較複雜、各階段要不同的檢查、可能跳回前面任何階段時，就考慮 graph。
- 再說一次：這些都應該是**自然出現**的——你要做的任何檢查、長成 loop 或 graph 的形狀，都是做幾次之後自然發現的。「難怪在外面很難找到什麼 loop 教學，或是教完了以後你完全聽不懂它在幹嘛」，因為不一定都要這樣做。
- 不用太在意詳細定義；有些問題簡單到下完 prompt 就結束，**不要因為 loop 流行，就以後絕對不下單純的 prompt**；有些問題到 loop 就很好，不用非弄到 graph。

**開專案**

- 專案資料夾裡事先只放了 `assets`（之後做投影片用的小貼圖），其他什麼都沒有。
- 找 Karpathy 的 LLM Wiki（搜尋「Karpathy LLM Wiki GitHub」；Gist 跟 GitHub 差在哪可以問 AI——Gist 只要傳一個檔案，不用建 repository），按 Raw 整段 copy（也可以叫它直接去參考）。
- New project → 選資料夾。**coding agent 裡大部分 project 就是綁一個資料夾**，很多習慣、概念都從寫程式來；Work Agent 不一定非綁不可，但綁資料夾是好習慣，也比較自然。
- 「最重要的一步做完了，就是跟它講我們資料夾在哪裡而已」——所有 agent 都長這樣，用別的工具只要學「怎麼告訴它我的專案資料夾在哪」。

**請 AI 訪談（交辦大意）**
> 我要做一個論文的 LLM Wiki 知識庫，會參考 Karpathy 的 LLM Wiki 做法（貼上全文）。在寫 AGENTS.md 之前，請先幫我釐清各種想法、確認目標，或我們的 AGENTS.md 要怎麼寫。目前專案資料夾裡的 assets 是之後做 HTML 簡報用的圖貼，先暫時不用在意。

- 這句話不用抄，愛怎麼說就怎麼說，**唯一重點是希望它訪問你**——「我們自己想不清楚的東西，就請它幫我們想清楚」，已經用過好幾次的常用技巧。
- 人家看到貼一大段會覺得很厲害，其實只是 copy 過來。
- 有特殊需求（不是標準 LLM Wiki 會做的）當然也可以跟它講，**作業裡也可以說明你做了什麼特殊設定**。

**AI 的訪談問題**（Coding Agent 的好處：會跳出選項讓你點，不用像上次一一打字）

| 問題 | 老師的選擇／說明 |
|---|---|
| 應用場景 | 專注某研究主題（碩博士做研究可選）vs. 稍微廣泛的某大領域 → 選後者（放 LLM 相關論文） |
| 平常收到的格式 | PDF（可多選）；arXiv 連結也可以讓 AI 自己抓 |
| 自動維護的知識點 | 單篇論文摘要、核心概念／方法頁、任務頁；「綜合比較」做論文研究可選，今天要的是學東西用的筆記 |
| 連結風格 | 雙向連結、相對路徑；筆記軟體選 Obsidian |
| 丟入一篇時 | 互動討論 vs. 全自動：**老師比較推薦互動討論**（做出來的 wiki 比較符合需求），示範讓它全自動 |

- 「剛好在打鐘的時候完成了所有的問題」——等一下看到 AGENTS.md 會非常感動：非常仔細、非常符合你的需求。

**下課回來（影片約 1:00 起）**：AI 規劃好結構（為符合 Karpathy 的結構放 raw、papers……），「看起來很高級，事實上我們什麼都沒做」。它又追問幾題，老師的回答：

1. 內文用**繁體中文**，技術性名詞用英文（照它的建議）。
2. 檔名格式依建議；論文頁用「**作者＋內容**」（只寫 Attention Is All You Need 常會忘記它在講什麼，所以加上 Transformer）。
3. 出現數學要保留，用 **LaTeX** 打出來。
4. 給 PDF 論文請放入 `raw/papers/`；給 arXiv 等連結請**下載 PDF** 放進去（它會自己抓，方便很多）。
5. 最後：「請依此建立 AGENTS.md，並建立其他需要的資料夾和檔案。」

**git init**
- 就是把這個專案交給 Git 管理。Git 跟 GitHub 不一樣：**Git 在你自己的電腦上就能管理專案**——搞爛了想回到「從前某一個美好的時光」、不小心刪了檔案想救回來，都做得到；Git 也天生很適合推到 GitHub 上。
- 不是老師帶著做，是「可愛的 AI 會帶著我們做」。**這些詞真的不用背**，想到什麼就跟它說什麼，最重要的是請它先跟你釐清需求。
- AI 該問的幾乎都問到了，有些沒問到也無所謂；你覺得重要的，可以請它再問。

**欣賞 AGENTS.md**
- 今天時間關係是「欣賞」，真的做的時候應該要**確認**。寫得整整齊齊：每個資料夾是什麼、要幹什麼、raw 檔有什麼規定。認真做時要仔細看，欠缺的再跟它講——「你會發現它大部分的地方考慮的可能比我們還要仔細」。

**Ingest 第一篇論文**
- 丟一篇大型語言模型與教育的論文：「請讀第一篇論文」。它其實設了好幾個當指令用的字，但**用口語說它都聽得懂**，因為它知道這是要幹什麼的。它開始讀論文、存成各種 wiki 的 .md 檔。
- 因為它想太久，課堂只做一篇；「**回去的時候請多丟幾篇**」，更看得出有趣好玩的地方。
- 跟上週唯一的不同：上週沒認真對談就直接下 prompt。上週通常也不會太差（很多都照它的建議走），但對談**更確定做得有沒有符合我們的需求**；做久了想到它建議裡沒提到的，也可以再提醒。
- 例：AGENTS.md 沒寫清楚「給它的文章要自己存到 raw 裡」，它就常會忘記——幫你讀了、還做了好的 wiki，偏偏沒把原文存進 raw（它覺得是你給的，你自己知道）。**不要假設它什麼都知道**；這個員工有時太聽話了，「一個口令一個動作，沒有口令就沒有動作」。

**wiki 長什麼樣子**
- wiki 是給 AI 看的，跟想像的 Wikipedia 有點不一樣，比較像**一段一段零碎的碎片**——很像做 RAG 時的切塊。Karpathy 自己也說本來想做 RAG，後來發現不做也可以。
- 複習 RAG：切成一塊一塊，把語意的部分做成**向量**（embedding），放不進向量的資訊放 **metadata**。LLM Wiki 是「天生很適合做 RAG 的長相」。

**用 Obsidian 看 wiki**
- Open vault → 開啟存在的資料夾 → 選 wiki。一小段一小段的文字，「有一點點零碎，但寫得還不錯」。
- 大家很喜歡 Obsidian 的另一個原因：按**關聯圖（Graph view）**就會畫出很酷炫的 wiki 關聯圖，文章越多越漂亮——「你真的什麼都沒有做」。

## 05. 實作二：主題 → HTML 簡報

### 5.1 今天的應用（P38）

說一個主題（例：多模態 RAG）〔使用者〕→ 只用 wiki 的內容〔AI〕→ 一份 HTML 簡報〔成品〕

> 同一個 wiki、同一個模型，要做的事也一樣，**只換做法**。

💬 老師補充：wiki 的目的是**幫我們學習**——丟很多 LLM 論文進去，請它用 wiki 的內容做出簡報型的教學，「看了我就懂了」。作業的目標不一定是教學，可以是任何簡報，例如幫自己的新創公司做簡報：每次需求不同，就要用資料庫做出不同的簡報。

### 5.2 Prompt：一句話（P39–P40）

> 你：根據 wiki 裡關於多模態 RAG 的內容，做一份 HTML 簡報。
> AI：做好了！

**然後你開始一直修**：

| | 問題 |
|---|---|
| 😵 | 第 5 頁字太多，跑出畫面 |
| 🔍 | 這個 37% 是哪篇的？ |
| 📚 | 8 篇相關論文只用了 3 篇 |
| 🔄 | 論文 A 的結論講反了 |

> 這裡也有 loop——只是**你自己就是那個 loop**。

💬 老師補充：你叫它修、它修一個新的 HTML、你看完又覺得「這到底在搞什麼東西」再叫它修……來來回回非常多次，可能修出一個還可以的版本，也可能永遠修不好。

### 5.3 Loop 版：把你的修正寫成規格（P41–P42）

`SKILL.md`：

| | 項目 | 內容 |
|---|---|---|
| 🎯 | 目標 | 只用 wiki，產出 HTML 簡報 |
| ✅ | 程式檢查 | 每頁有出處、引用頁面存在、數字找得到、8–15 頁、渲染後沒有溢出 |
| 🧑‍⚖️ | AI 審查 | 新對話，只給簡報和引用頁，檢查忠實度和覆蓋率 |
| 🔁 | 每一輪 | 只修檢查報告列出的問題 |
| 🛑 | 停止 | 全過／改滿 3 輪／相關頁面少於 3 頁就一開始停下 |

**跑起來是這樣**（P42）：

| 輪次 | 結果 |
|---|---|
| 第 1 輪 | 腳本：3 頁溢出、2 處沒出處；審查：第 6 頁講反了 |
| 第 2 輪 | 腳本：全過；審查：論文 D 沒用到 |
| 第 3 輪 | 補進論文 D → 全過 → 交件，附檢查報告 |

> 「我只要最後看報告就好！」

💬 老師補充：
- 聽到「規格書」，希望大家馬上有個想法：**規格書不應該我們自己寫，應該請 AI 幫我們寫**。
- 規格要告訴它：做出簡報後**先自己檢查**，不要馬上交給我——「我是大老闆，我沒有想要看你這個隨便亂做出來的結果」；希望特別檢查的地方請它檢查；每一輪只修報告列出的問題；例如三回合後才出結果。
- 大老闆只要看結果，也可以看檢查報告——裡面會寫過程中碰到什麼、改了什麼。

### 5.4 Graph：先畫好流程（P43）

```text
檢索 wiki → [覆蓋率關卡] → 證據卡（平行） → 大綱 → [人工確認]
              不足→停下                              退回→修大綱或補檢索
→ 逐頁稿 → [忠實度檢查] → 渲染 HTML → [渲染檢查] → 交件
            退回→只修那頁                 退回→逐頁稿
```

- 圖例：AI 節點／人工確認／檢查關卡；橘字＝退回路線。

### 5.5 每一關只能看什麼、改什麼（P44）

| 節點 | 只能看 | 不能做 |
|---|---|---|
| 證據卡 | 一篇論文 | 混入其他來源 |
| 逐頁稿 | 大綱＋對應卡片 | 引用卡片以外的內容 |
| 渲染 HTML | 已通過的逐頁稿 | 改任何一個字 |
| 檢查關卡 | 成品＋來源 | 自己動手改 |

> 排版時想順手改句子？**不行！**

### 5.6 錯在哪一關，就退回哪一關（P45）

| 狀況 | 處理 |
|---|---|
| 📄 第 6 頁講錯 | 只修那頁，其他 14 頁不動 |
| 🃏 卡片本身錯 | 退回重抽那一篇的證據卡 |
| ✂️ 字太多 | 不是硬塞，退回逐頁稿縮短 |
| 🧩 缺子題 | 人看大綱時發現，退回檢索補資料 |

> **退回路線是你事先設計好的。**

### 5.7 每一格裡面，還是 loop（P46）

| 節點 | 小 loop |
|---|---|
| 逐頁稿節點 | 寫一頁 → 檢查出處 → 修（最多 2 輪） |
| 渲染節點 | 產生 HTML → 截圖 → 修版面 → 再截圖 |

> **graph 決定大流程，loop 負責每一格的反覆修正。**

|---|---|---|---|

### 💬 5.10 課堂示範：一句話 → 設計風格 → graph 版（影片約 1:17 起）

**測試一：一句話 prompt**
> LLM 在教學上要注意什麼？請用 wiki 的內容，把它做成 HTML 簡報式的投影片，放到一個適當的資料夾裡。

- **故意說得很含糊**（連資料夾名稱都沒指定），看它做成什麼樣子。全部都是當場示範，好處是大家看得到「真的是這樣做出來的」。
- 成果放在 `slides/`：「還可以啦，沒有真的很糟糕」。它有想到要用貼圖，但**貼圖路徑寫錯、圖顯示不出來**——細節要自己檢查。因為時間關係沒叫它改，改成在 slides 資料夾也放一份貼圖。

**設計簡報風格**
> 先設計網頁的風格：日式可愛、粉彩風格，可以多用圖貼（slides 資料夾也有一份），圖的路徑要寫好。再一次，請先訪問我問題來釐清需求。

- 剛剛看到的問題，就直接跟它講。
- 擔心它推薦的你不喜歡，可以像上週一樣請它**先設計三個範本**再選。
- 選項包括固定角色、小圖點……；用途選「**圖文講義型**」（自己學習用），而不是演講、課堂用。
- 不滿意（例如字有點小）可以重複很多次直到滿意；**滿意之後它以後都會照這個設計做**。（上課時間關係「不管滿不滿意都要接受」）

**Graph 版**
- loop 跟 graph 時間只夠示範一個，問大家沒意見，就選 graph——「因為聽起來比較高級」。用 loop 也沒什麼特別：跟它說「我要用 loop，幫我設計做投影片的完整流程」就好。
- prompt 大意：「現在要用 graph 的方式思考做投影片，請再一次協助釐清，**先把流程畫出來參考，不要先定案**。我希望先整理一份大綱，大綱確認後再做逐頁內容，最後做成投影片。因為要設計成 graph，請想清楚各階段如何檢查。」
- 為什麼要先做**逐頁內容**？可以叫它直接做出投影片，但以後很難修改；先生成逐頁內容，就能改每一頁、比較符合需求。但逐頁內容對人不是那麼好讀、也沒想像中好改，所以**檢查點放在大綱比較方便**。
- AI 畫出流程（還「狗腿地」稱讚你說得太棒）：觸發簡報任務 → 寫大綱 → 自我檢查 → **使用者檢查大綱** → 逐頁內容 → 做出投影片。它也會問：中間產物放哪（當然存起來）、人工確認關卡停幾次（只要檢查大綱）、要不要自動排版檢查、要不要保持多樣性……看大家高興。
- 定案：「把剛剛要做的投影片，用這個流程做一次。」

💬 老師補充：
- **檢查大綱是人最擅長的**：很容易看出該講的沒講、哪裡講不清楚，比檢查逐頁投影片容易——「你不要自己找自己麻煩」。大綱一定要檢查，因為 AI 想像的有時跟你不一樣；後面就希望全自動化。
- 每一關發現不適宜，可以叫它改（退回重做）或自己改，也可以設計更多關卡。**中間其實有很多小 loop**，不是每一關都要你去設。
- graph 也沒什麼了不起，AI 會協助你設計好，但**你要看懂它在做什麼**。P43 那張圖跟剛剛 AI 畫的差不多，只是把檢查關卡畫得跟一般關卡一樣大；檢查關卡要告訴它「不對時退到哪邊重做」。覺得那種圖比較清楚，也可以請 AI 畫成那樣給你看。
- **Git 其實跟它講就好**：「這個專案想用 Git 管理」它就會做；也可以問它「我想把專案放到 GitHub，每次更新要怎麼告訴你，你才會幫我推上去？」作業**不強制**照 Git 流程（但很推薦），第一次有點複雜，之後就輕鬆快樂——出一張嘴說「push 到 GitHub」它就幫你 push。
- 只看結果或看別人的 GitHub，會覺得超複雜、自己怎麼做得出來；但跟著課程走到現在就知道，大部分事情是 AI 做的，我們像大老闆在旁邊喝咖啡、滑手機，回來看它做好了沒——它做到一半也可能會問我們意見。

## 💬 助教時間：第九週作業解說（影片約 2:25 起）

### 作業怎麼拿高分？

| 基本要有的 | 拿高分的關鍵 |
|---|---|
| 標題格式正確、要求的每一項都有交 | 說得出「這是給誰用、解決什麼問題」 |
| Colab 程式作業：共用權限有開、程式能執行、用 Markdown 標出重點 | 說清楚你為什麼這樣設計 |
| 文字繳交作業：網站連結打得開、有介面截圖、有規格和修改過程 | 寫出和 AI 對話時做的關鍵決定 |
| | 反覆測試、發現問題、再改良 |
| | 附操作說明，截圖旁寫一句在展示什麼 |

- **AI 做得出作品，寫不出你的想法！** 大家跟 AI 協作做出的作品都「差不多好」，要不一樣就要加進自己的想法。
- **把你的關鍵決定寫出來**（照 4 段寫，有條理又完整）：① 我想做什麼（目標、為什麼選這個題目）→ ② AI 給了什麼（你問了什麼、AI 提出哪些做法）→ ③ 我怎麼決定（採用或捨棄哪個、理由）→ ④ 測試後改了什麼（發現什麼問題、怎麼改、用什麼證明改好了）。不要只截圖 AI 的回答，要寫出你怎麼判斷。
- 助教說：原本可能只拿七、八分，加上這些細節就可能拿到九分或十分。

### 第九週作業：建立一個自己的 AGENTS.md 或 CLAUDE.md

- **繳交期限：11/16 23:59**（遲交到 11/17 16:00）。標題格式：學校 學號 系級 姓名 主題（學校、系級打簡稱；主題可省略）。
- 內容要有這五項：1. 專案簡介　2. GitHub Repository 連結　3. 網頁連結　4. AGENTS.md 或 CLAUDE.md　5. 規則如何幫 AI 繼續新增內容
  - 第 5 項要寫：你寫的哪些規則，讓 AI 下次能自己做對？例：命名與資料夾規則 → AI 知道新檔案叫什麼、放哪裡；模板與固定段落 → 新頁面的格式跟舊的一致；完成檢查清單 → AI 做完會自己確認目錄有更新、連結沒壞。
- **少了這些會被扣分**：沒有連結或連結打不開 → 最多 6 分；只有網頁，repo 裡沒有 AGENTS.md／CLAUDE.md → 最多 3 分。
- **先選一個「會一直長大」的題目**（問自己：之後會想再加第 2 篇、第 10 篇嗎？）：讀書筆記（每讀一章加一篇）、課程講義（每上一週加一份）、作品集、美食地圖、影評書評、社團紀錄……不太適合：只有一頁的自我介紹、辦完就結束的活動頁。
- **交作業前檢查這 5 件事**：
  1. 網頁連結要是能打開的公開網址 `帳號.github.io/...`（不行的例子：`http://localhost:8000`、`http://127.0.0.1:8000`——AI 在你的終端機開的本機預覽，別人打不開）
  2. Repository 設成 **Public**，不然網頁不會出來
  3. AGENTS.md 推上 GitHub，放在專案最外層
  4. AGENTS.md 裡要有**新增頁面的規則**：格式、命名、放哪裡
  5. **不在專案中放個資、密碼、API key**（推上 GitHub 大家都看得到，很容易被盜用）
  - 交之前用**無痕視窗**打開自己的網頁連結，確認別人也看得到！

### 為什麼要寫 AGENTS.md？

- AI 每次開新對話，都像**第一天上班的新同事**，前面講過的全忘了。

| 沒有 AGENTS.md | 有 AGENTS.md |
|---|---|
| 每次都要重講一遍規則 | 一句「請先讀 AGENTS.md」就接上 |
| 每次做出來的格式都不一樣 | 每次都照同一套格式做 |
| 對話越聊越長，越來越耗額度 | 可以放心開新對話，省額度 |
| 換台電腦、換個 AI 就接不上 | 規則跟著專案走，誰接手都看得懂 |

- 💬 助教：沒寫清楚的話，換新視窗它會依自己的推斷亂加功能、改按鈕風格，整個專案就變得很奇怪。

### 這麼多 .md 差在哪？（先看是寫給誰看的！）

| 檔案 | 寫給誰看 | 什麼時候讀 | 寫什麼 |
|---|---|---|---|
| README.md | 人 | 第一次打開專案 | 專案介紹、怎麼預覽、怎麼部署 |
| AGENTS.md | AI | 每次開新對話 | 專案規則、不能做的事、該讀哪份文件 |
| SKILL.md | AI | 遇到符合的任務才讀 | 某件事的詳細步驟（SOP） |
| PRD.md（產品規格書） | 人和 AI | 規劃專案功能時 | 要做什麼、不做什麼、怎麼驗收 |
| DESIGN.md | 人和 AI | 改樣式、做新頁面時 | 顏色、字體、間距、元件長相 |

- 全部都只是 Markdown 文字檔，差別在**誰讀、什麼時候讀**；CLAUDE.md 跟 AGENTS.md 是同一種檔案，只是給 Claude 用的名字。
- 💬 助教：任務分很多種時拆成 SKILL.md，做那個功能時才讀，token 用得比較少。

### 什麼時候要把 AGENTS.md 拆開？

- 出現這些情況再考慮：1. 檔案長到 AI 開始漏看規則　2. 專案有好幾種任務（加內容、改樣式、加功能）　3. 很多規則只有某一種任務才用得到　4. 不只一個人在維護，各自負責一份
- **這次的作業：全部寫進一份 AGENTS.md 就可以！**（目的、風格、頁面結構、新增內容的規範、AI 修改規則，都放在同一份）
- 拆開後 AGENTS.md 還是要留：專案目的、開發規範（技術限制、命名）、新增內容 SOP、不能做的事、完成檢查，再加一句「改樣式讀 DESIGN.md、加功能讀 PRD.md」指過去。

### 呆一布講義怎麼做到的？（一套可以一直重複的生產線）

- **CLAUDE.md**（同 AGENTS.md）＝專案憲法：品牌色、字體、工作流程
- ＋ **固定資料夾做存取**：每份講義一個英文 slug，三個地方名稱一致
- ＋ **參考範本**：做好的第一份講義＋共用素材庫
- 它的鐵則：一定先寫好逐頁內容稿 `slide-notes/講義名稱.md`，才讓 AI 做網頁。

### AGENTS.md 可以這樣分段（範例：筆記網站）

| 段落標題 | 寫什麼 |
|---|---|
| `## 專案目的` | 整理各門課的筆記與複習，一個主題一篇 |
| `## 網頁風格` | 米白底、深灰字、螢光黃只用在重點 |
| `## 頁面結構` | 首頁＝依課程分組的目錄；筆記頁＝單篇內容 |
| `## 檔案與命名` | `notes/課程/主題英文小寫.md`，例如 `sql-join.md` |
| `## 新增內容的步驟` | 複製模板 → 照固定四段寫 → 登記到目錄 |
| `## AI 修改規則` | 不動既有樣式、不刪舊筆記、做完照清單檢查 |

- 每段寫幾行就好，重點是 AI 讀完知道「下一頁該怎麼做」。

### AGENTS.md 寫得好不好？（開新視窗測一次就知道！）

1. **開新對話**：AI 沒看過你們之前的討論
2. **丟一份新資料**：只說一句話，不多做說明（例：「請先讀 AGENTS.md，把下面這段講義整理成一篇筆記。」）
3. **對照預期**：做出來的跟你想的一不一樣？（檔名和放的位置對嗎？格式跟舊的頁面一樣嗎？首頁目錄有更新嗎？有沒有動到不該動的檔案？）
4. **補規則再測**：做錯的地方，就是規則沒寫清楚的地方

- **為什麼用 Antigravity？** 要能「讀檔、改檔」的 AI：1. 打開整個專案資料夾（讀得到 AGENTS.md，自己建檔、改檔、跑指令）　2. 先給計畫再動手（可以先審、留言修改，同意了才執行）　3. 學生方案就能用（申請 Google AI Plus 就有額度）。有付費其他 AI 也可以：ChatGPT Plus 以上 → Codex（直接讀 AGENTS.md）；Claude Pro 以上 → Claude Code（讀 CLAUDE.md，沒有時會讀 AGENTS.md）。工具可以換，規則檔跟著專案走！
- **Antigravity 開始前先設定好**（只要做一次）：1. 用個人 Gmail 登入（Continue with Google）　2. 讓 AI 做完計畫直接執行（Agent Behavior 的 Plan Review Policy → Always Proceed，就不用一直按同意）　3. 建立專案資料夾（放在 `C:\Users\你的名字\` 底下）　4. 選模型 Gemini 3.8 Flash（Plus 也能用）。另外先裝好 Git for Windows，並在 GitHub 建一個空的 Repository。

### 做完會長這樣（AGENTS.md 一定放在最外層！）

| 檔案 | 用途 | 誰做 |
|---|---|---|
| `AGENTS.md` | 給 AI 的規則，AI 開工前會先讀 | 你要寫的 |
| `README.md` | 給人看的說明，可有可無 | 你要寫的 |
| `index.html` | 網站首頁，GitHub Pages 從這裡打開 | AI 幫你做的 |
| `style.css`、`app.js` | 樣式和程式，檔案少就直接放最外層 | AI 幫你做的 |
| `images/` | 網站用到的圖片，集中放一個資料夾 | AI 幫你做的 |
| `notes/` | 你的筆記或資料，照 AGENTS.md 的規則放 | 之後一直新增 |

- 💬 助教：圖片和筆記不要隨便亂存在專案裡，路徑沒指好的話 AI 會找不到檔案，丟上去可能就「變一坨」。

### 實作步驟（助教示範）

**Step 1 先跟 AI 討論出 AGENTS.md**

> 我想做一個「個人筆記整理網站」。先不要寫任何程式，請先跟我討論，幫我寫一份 AGENTS.md，內容要包含：專案目的（筆記一個主題一篇）、運作方式、技術限制（不用框架、能放 GitHub Pages）、檔案結構與命名、新增筆記的固定格式、只整理我給的資料、視覺風格、修改規則與完成檢查清單。但我現在還不清楚詳細需求，你可以用問問題的方式問我，釐清我的需求，先不要建立其他檔案。

- 寫好後打開 Overview Panel 讀一遍，有漏掉的規則就請 AI 補上（例：同主題要合併進舊筆記）。
- 💬 助教的例子：讀完發現少了需求——希望每篇筆記的重點知識都有圖解說，但不想讓它亂生圖，所以要求**用 HTML 畫圖、嚴格遵守文章內容**；又想到有些筆記已有對應圖片，就請它「已有的用現有圖片，重點處沒有的才生成」。滿意後請它寫進資料夾，它連資料夾架構都寫好了。

**Step 2 開新對話，建網站**（AI 會先列計畫，再自己一路做完！）

> `/plan` 請先讀 AGENTS.md。依照裡面的規則建立網站與兩篇範例筆記，完成後告訴我建立了哪些檔案。

- `/plan` 是什麼？打在指令最前面，AI 會先寫出「要建哪些檔案、怎麼做」的計畫，再開始動手。
- 流程：列出計畫（Implementation Plan）→ 自動執行（Always Proceed）→ 逐項打勾（Task List）→ 看成果（Walkthrough）。
- 💬 助教：要預覽時它會說去終端機執行；不知道怎麼開就直接請它在終端機執行，它會跳出本機連結（只有你的電腦打得開）。想自己玩終端機可以請它教你：`ls` 列出資料夾、`cd Documents`（按 Tab 自動補齊）進入資料夾、`cd ..` 回上一層、`clear` 清畫面，再執行它給的 Python 指令（要先裝好 Python）。（示範時遇到網站顯示零篇筆記、檔案不見的狀況，課堂上沒有解決）

**Step 4 把網頁放上網**（投影片所示，課堂快速帶過）

1. 請 AI 推上 GitHub（大意：「把資料夾初始化成 git repo，推到我建好的 github.com/帳號/my-notes」）
2. 第一次會跳出登入視窗：在瀏覽器登入 GitHub 即可
3. 開 GitHub Pages：Settings → Pages → main／(root)
4. 等 1–2 分鐘打開網址：`帳號.github.io/my-notes/`

- 💬 助教：新建 Repository 時建議**先不要勾 README**，保持空專案比較好推——如果雲端已有檔案，要先拉到本地端才能推上去，對新手比較麻煩。複製 repo 網址給 AI，它會自己開終端機輸入 Git 指令推上去；對 Git 指令有興趣可以上網學，也滿有趣的。

**今天的重點**：① AGENTS.md 是給 AI 的員工手冊（寫成檔案，每次開新對話都能接上，不用重講）　② 開新對話測一次 AGENTS.md（做不好的地方，就是規則沒寫清楚的地方）　③ 用 Agent 工具，一句話就能繼續做（專案不是做完就結束，而是可以一直長大）——作業 **11/16 23:59 截止**，這週就開始做！

| Loop Engineering | 設計 loop 的功夫：寫目標、限制、完成標準、停止條件、觸發；Addy Osmani 於 2026 年 6 月命名 |
